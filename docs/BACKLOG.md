# Развитие после бонусов

Реализованы RUB/BTC/USDT с конвертацией, UTM-группировка/фильтры, Telegram LTV lookup, Prometheus/Grafana, JSON slog и GitHub Actions. Детали и границы: [BONUSES.md](BONUSES.md), [OPERATIONS.md](OPERATIONS.md), [TESTING.md](TESTING.md).

## Дальнейшее развитие бонусов

- Подключить настоящий исторический FX provider вместо синтетических котировок mock-набора; отдельный ingest/backfill, аудит версии курсов и отказоустойчивость. Клиентские запросы остаются привязаны к опубликованному снимку.
- Добавить выбор отчётной валюты с документированной датой оценки; текущая отчётная валюта RUB фиксирована.
- Для реального crypto gateway вводить network/token identity и нормализацию decimals; обработка блокчейн-транзакций вне аналитического сервиса.
- Историческая UTM-атрибуция first-touch/last-touch и версии исправлений вместо одного поля пользователя.
- Авторизация и аудит доступа к финансовому профилю Telegram пользователя.

## Развитие мониторинга

HTTP/Go-метрики, синхронизация, источники, кеш, PostgreSQL/Redis, четыре дашборда и базовые alert rules реализованы. Текущий состав и проверка описаны в [OPERATIONS.md](OPERATIONS.md).

Следующие улучшения:

- Настроить Alertmanager и получателей уведомлений после выбора канала владельцем сервиса.
- Подобрать SLO и пороги алертов по результатам нагрузочных проверок.
- Добавить request/sync correlation ID и связь логов с дашбордами.
- Добавить счётчики страниц и строк каждого источника, не включая ID записей в labels.

Приёмка: уведомления проверяются тестовым событием, пороги документированы, labels остаются ограниченными, пароли и персональные данные не попадают в метрики.

## Динамические источники и инкрементальная загрузка

- Добавить отдельный управляемый сценарий генерации событий после seed: новые пользователи, retry, refund и смена тарифа. Базовый seed остаётся воспроизводимым и идемпотентным.
- Для изменений во время пагинации спроектировать source snapshot token или версионируемый high-watermark. Timestamp-фильтр и offset pagination без такого протокола не гарантируют стабильный набор при конкурентных изменениях.
- Поддержать tombstones для удалений, разделить курсоры по источникам, определить правила поздних событий и первоначальной повторной загрузки.
- При появлении тарифных изменений сохранять цену оплачиваемого периода в данных операции/версии тарифа; текущая цена тарифа не должна переписывать историческую выручку.
- Для реальных оплат явно определить допустимую задержку продления, entitlement после refund и partial refunds. Новая политика должна иметь отдельные ручные fixtures и документированную совместимость.

Приёмка: изменения между страницами не теряются, повторная доставка безопасна, старый refund попадает в следующий снимок, курсоры не двигаются при неуспехе, результаты полного и инкрементального пересчёта совпадают.

## Хранение и масштабирование

- Нормализовать подготовленные факты в таблицы с индексами по snapshot, первой подписке, тарифу и UTM; измерить планы запросов, прежде чем добавлять индексы.
- Заменить поштучные inserts массовым `COPY`/batch import; уменьшить время PostgreSQL writer transaction, сохранив единственную точку публикации.
- Вынести существующие idempotent-миграции v1/v2 из bootstrap в отдельные версионированные SQL-файлы и инструмент с проверкой совместимости и процедурой отката. Изменение генератора не должно незаметно менять существующий seed.
- Для нескольких analytics-реплик добавить единственного sync leader и координацию одинаковых вычислений между процессами. Текущий `singleflight` объединяет запросы только внутри одной реплики.
- Сделать повторяемую очистку retired namespaces после восстановления Redis; сейчас недоступность Redis во время GC может оставить неиспользуемые ключи.
- Добавить backup/restore PostgreSQL и проверку восстановления; Redis остаётся восстанавливаемым кешем, а не источником финансовых данных.
- Для внешнего production-доступа добавить TLS, аутентификацию, лимиты запросов и управление credentials; протестировать согласованную ротацию PostgreSQL-паролей.

Приёмка: опубликованный snapshot не смешивается с предыдущим при масштабировании и очистке; restore восстанавливает выдачу без доступных источников; конкурентные фильтрованные запросы не запускают одинаковые тяжёлые расчёты на всех репликах.

## Дальнейшее развитие проверок и CI

CI запускает Go race с PostgreSQL/Redis, линтер, frontend typecheck/ESLint/Vitest/build/browser tests и Compose/live smoke. Дальнейшие проверки — обновление миграций на сохранённых production-like volumes, потеря соединения в момент ответа COMMIT, рестарты PostgreSQL/Redis, ограничение памяти, длительные нагрузочные прогоны и периодическая проверка зависимостей. Транзакционный rollback при отказе COMMIT уже проверяется integration-тестом. Каждое расширение должно иметь измеримый сценарий, а не только увеличение процента покрытия.
