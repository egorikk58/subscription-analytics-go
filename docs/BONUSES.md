# Реализованные бонусы

## RUB, BTC и USDT

Тарифы задаются в RUB. Платёж хранит исходную положительную сумму `amount` в atomic units своей валюты: RUB — 2 знака, BTC — 8, USDT — 6. USDT здесь — нормализованный ledger asset; обработка блокчейнов и контрактов не входит в аналитический сервис. Для подключения реального платежного шлюза нужны отдельные network/asset ID и нормализация native decimals провайдера.

Криптоплатёж содержит `fx`: идентификатор котировки, `rub_per_unit` (десятичная строка RUB за 1 BTC/USDT), `as_of` и `source`. RUB конвертируется тождественно. Клиентские запросы не получают сетевые котировки: исходный payments API отдаёт историческую котировку вместе с оплатой, фоновая загрузка проверяет её и замораживает в снимке.

Полный набор использованных котировок сохраняется в `analytics.snapshots.data.exchange_rates` вместе с conversion policy, а не только в образцах платежей. Повтор одного (currency, quote ID) с другими значениями отклоняется. Финансовые агрегаты и метаданные курсов публикуются одним commit.

Моки используют **синтетические месячные курсы** `deterministic-demo-fixture-v1`, а не биржевые цены. Это осознанный выбор для воспроизводимого тестового: одинаковые seed, даты и версия дают одинаковые native суммы и рублёвые результаты. Внешнего FX-провайдера и live trading цен нет. Котировка должна быть положительной, точной и не позднее времени оплаты; отсутствие обязательной котировки отклоняет новую публикацию и сохраняет старый снимок.

```text
RUB minor = round_half_away_from_zero(
    native_amount × rub_per_unit × 100 / 10^asset_decimals
)
```

Конвертация использует `big.Rat`/`big.Int`, без float64. Округление одно, на уровне оплаты. Итог проверяется на int64. Два satoshi при курсе 50 000 000 RUB/BTC дают 100 копеек; 10 000 atomic USDT при курсе 100 RUB/USDT также дают 100 копеек. Эти значения — ручные тестовые примеры, не рыночные котировки.

Полный возврат копирует amount, currency и fx исходной успешной оплаты. Он вычитает её исходную рублёвую стоимость, поэтому курс в день возврата не создаёт прибыли/убытка. Несовпадение исходной оплаты, периода, суммы, валюты, котировки и повторный refund отклоняются. Failed attempts не дают выручки. Платёж после перевода в RUB должен соответствовать цене тарифа.

Все LTV endpoints, графики, среднее и медиана возвращаются в RUB; `ltv` и `total_revenue_minor` — копейки. Выбор произвольной отчётной валюты не реализован: в запросах нельзя смешать активы или динамически пересчитать старый снимок по сегодняшнему курсу. Суммы JSON int64 клиенты должны читать с поддержкой точных 64-bit integers.

## UTM

```http
GET /metrics/ltv/by-utm?page=1&page_size=100
GET /metrics/ltv/summary?utm_link=campaign-1
GET /metrics/ltv/by-plan?utm_link=campaign-1
GET /metrics/retention?plan_id=monthly&utm_link=campaign-1
GET /api/dashboard?utm_link=campaign-1
```

`by-utm` содержит groups с users_count, total_revenue_minor, mean_ltv_minor, median_ltv_minor; total — число групп до пагинации. Группы сортируются по utm_link. page: 1..1 000 000, page_size: 1..1000, default 100.

Атрибуция берётся из user.utm_link и сохраняется в Facts. Пробелы по краям удаляются, регистр сохраняется. Пустой источник и зарезервированный `unknown` образуют группу «Без UTM». Не передавать параметр — все источники; `utm_link=` или `utm_link=unknown` — без атрибуции. Значение ограничено 2048 байтами. Поздние исправления поля в источнике попадут в следующий снимок; это не система исторического last-touch attribution.

Фильтр комбинируется с датами первой подписки; lifetime оплаты не обрезаются датами. Retention сохраняет правила зрелости и переходов между тарифами. Нулевые LTV входят в группы. UTM включён в cache keys, а не Prometheus labels.

Frontend показывает общий UTM-фильтр и таблицу сравнения источников на обзоре/выручке. Нажатие на источник применяет фильтр ко всем соответствующим графикам и таблицам. Список вариантов строится по полному снимку, поэтому выбранный фильтр не прячет остальные варианты. Preview также поддерживает UTM.

## LTV по Telegram ID

```http
GET /users/by-telegram/1000007919/ltv
```

Ответ: user_id, telegram_id, first_plan_id, ltv, payments_count, current_status, currency, data_as_of. LTV — net RUB minor units. first_plan_id=null без подписки. payments_count — число succeeded записей, включая впоследствии возвращённые исходные оплаты; failed и refunded записи в счётчик не входят.

Статус берётся из последней подписки по (started_at, id), не находящейся в будущем. `active` с закончившимся current_period_end становится `expired`; без подписок — `none`. Это состояние подписки, а не подтверждение оплаты; retention определяется платежами.

ID парсится напрямую как положительный десятичный int64: 1..9223372036854775807. Невалидный ID — 400, неизвестный — 404, отсутствие подходящего снимка — 503 + Retry-After. До первой публикации format_version=2 после обновления старый снимок не выдаётся за готовый Telegram index.

При публикации снимка транзакционно создаётся `analytics.user_ltv(snapshot_id, telegram_id, body)`. Составной PK обеспечивает индексированный lookup без обхода сырых оплат и обращений к мокам. Положительные и отрицательные ответы кешируются по версии в PostgreSQL и Redis; singleflight объединяет одинаковые обращения. При отказе Redis индекс и PostgreSQL cache продолжают работать. Истёкшие снимки удаляют индекс каскадно. ETag/304 поддерживаются для найденного профиля; HTTP Cache-Control private, no-cache.

На странице пользователей доступна форма lookup опубликованного снимка. В режиме preview она скрыта: preview не подменяет реальные данные Telegram endpoint. Форма передаёт ID строкой и показывает исходный JSON без потери int64 при JSON.parse.

## Prometheus и slog

Существующие HTTP, Go/process, sync, source, cache, PG и Redis метрики сохранены. Добавлен `subscope_dataset_payment_records{currency}` с ограниченным набором RUB/BTC/USDT. Это число всех payment records, включая failed/refund, а не финансовая сумма. Новый график находится в Grafana Sync/Cache.

Маршруты by-utm и Telegram lookup учитываются HTTP middleware. Telegram ID заменяется шаблоном `/users/by-telegram/{telegram_id}/ltv`; UTM, ID, query strings, пароли и тексты ошибок не используются в labels.

JSON slog содержит service и события запуска/синхронизации; HTTP completion — method, шаблон route, status, duration_ms и response_bytes. Health/assets не создают completion-логи. Миграция пишет версию и число подготовленных записей. Логи не содержат Telegram ID, UTM, raw query или исходные платёжные payloads.

## Обновление существующей БД

Bootstrap добавляет таблицу user_ltv и schema version 2. Новый генератор сохраняет config v2. Для v1 с теми же seed/count/months/as_of выполняется **транзакционная миграция демо-платежей**: IDs, число записей и рублёвая стоимость остаются прежними, часть RUB-платежей переводится в BTC/USDT, refunded получает native сумму/котировку оригинала. updated_at продвигается для следующей инкрементальной загрузки. Изменение параметров по-прежнему даёт ошибку, а не пересоздание данных. Повторный v2 bootstrap идемпотентен.

Существующие пользовательские UTM не переписываются; новые v2 datasets дополнительно гарантируют пользователей без UTM. Новые cache keys имеют версию формата; старые ответы не маскируют новые поля. PostgreSQL commit по-прежнему единственная точка публикации.

Версия мигрированного набора — `v2-migrated`, нового — `v2`. Это различает происхождение: у мигрированного набора сохранены прежние UTM/коррекции источников и продвинут updated_at. Его fingerprint не выдаётся за fingerprint свежей генерации по тем же seed/границам. Повторный запуск не повторяет миграцию.

Миграция синтетических оплат уместна для этого mock-набора. Для настоящих транзакций изменение исторической валюты недопустимо: потребовался бы импорт нативных полей провайдера, сверка и отдельная backfill-процедура.

CI настроен в `.github/workflows/ci.yml`: Go race с PostgreSQL/Redis, линтер, frontend types/lint/unit/browser и проверка свежего Docker-стека с настоящим API. Те же сценарии можно запускать локально; команды и границы проверок описаны в [TESTING.md](TESTING.md).
